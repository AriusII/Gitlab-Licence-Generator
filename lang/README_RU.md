## Что это такое

Инструмент, который генерирует самоподписанную лицензию **GitLab EE Ultimate** — **только для локального использования и разработки**.

Он делает ровно одну вещь: генерирует пару RSA-ключей и файл `.gitlab-license`, предоставляющий максимальный набор прав, который может нести офлайн-лицензия — все функции EE Ultimate, все дополнения GitLab Duo и другие дополнения на основе мест, практически неограниченное число пользователей и срок действия, истекающий в далёком будущем.

**Чего этот инструмент не делает**: он никогда не подключается к работающему экземпляру GitLab, не выполняет в нём развёртывание и не настраивает его. Подключение сгенерированного ключа/лицензии к вашему собственному развёртыванию GitLab — это ручной шаг, который вы выполняете самостоятельно (см. раздел [Установка лицензии](#установка-лицензии) или пример `docker-compose` ниже).

**Работает сразу «из коробки»**: готовая к использованию пара RSA-ключей (`keys/`) поставляется в этом репозитории в зафиксированном виде, поэтому для немедленного получения рабочей лицензии достаточно клонировать или форкнуть репозиторий — никаких дополнительных настроек не требуется. Из-за этого пара ключей одинакова во всех клонах и форках; см. примечание по безопасности в разделе [Конфигурация](#конфигурация), если это важно для вашего сценария использования.

**Конфигурация задаётся только через настройки, а не через флаги CLI.** Всё управляется через `appsettings.json` (поставляется вместе с инструментом) и, для автоматизации, через переменные окружения. Никаких параметров командной строки изучать не нужно.

> Набор функций и дополнений сверен с файлом `ee/app/models/gitlab_subscriptions/features.rb` репозитория gitlab-org/gitlab (ветка master / линейка 19.x).

## Получение лицензии

### Вариант А — Docker Compose (рекомендуется)

```bash
git clone https://github.com/Lakr233/GitLab-License-Generator.git
cd GitLab-License-Generator
docker compose up --build
```

Это соберёт образ (в который уже включена пара ключей по умолчанию из репозитория) и запишет лицензию в `./output/result.gitlab-license`. Каждый запуск также копирует тот самый публичный ключ, которым она была подписана (`public.key`), в `./output/` — это единственный ключевой материал, который вообще нужен самому GitLab, поэтому лицензия и ключ для её установки оказываются вместе, в одном каталоге. Приватный ключ остаётся только в `./keys/`. Контейнер запускается один раз и завершает работу — запустите `docker compose up` повторно в любой момент, когда потребуется пересоздать лицензию.

Чтобы изменить любую настройку, отредактируйте блок `environment:` в `docker-compose.yml`:

```yaml
services:
  glgen:
    build: .
    volumes:
      - ./keys:/license-generator/keys
      - ./output:/license-generator/output
    environment:
      License__Name: "Tim Cook"
      License__Company: "Apple Computer, Inc."
      License__Email: "tcook@apple.com"
      License__Plan: "ultimate"
      License__UserCount: "2147483647"
      License__ExpireYear: "2500"
      License__IncludeAddOns: "true"
```

### Вариант Б — обычный `docker run`

```bash
docker run --rm \
  -v "./keys:/license-generator/keys" \
  -v "./output:/license-generator/output" \
  -e License__ExpireYear="2500" \
  ghcr.io/lakr233/gitlab-license-generator:main
```

Без монтирования `./keys` контейнер просто использует встроенную в образ пару ключей по умолчанию (детерминированную, одинаковую при каждом запуске). Монтируйте `./keys` только если хотите сохранять между запусками *пересозданную* собственную пару ключей (см. `RegenerateKeys` ниже) — в остальных случаях это необязательно. В любом случае каждый запуск копирует использованный публичный ключ в `./output/` рядом со сгенерированной лицензией — это единственный ключевой материал, который нужен самому GitLab; приватный ключ остаётся в `./keys/`.

### Вариант В — из исходного кода (требуется .NET 10 SDK)

```bash
git clone https://github.com/Lakr233/GitLab-License-Generator.git
cd GitLab-License-Generator
dotnet run --project src/GitlabLicenseGenerator.Cli
```

Результат тот же, что и в вариантах с Docker: пара ключей в каталоге `keys/` и лицензия в каталоге `output/`, при этом рабочим каталогом служит корень репозитория. Каждый запуск также копирует публичный ключ в `output/` рядом с лицензией — приватный ключ остаётся в `keys/`.

### Вариант Г — GitHub Actions (не требует установки)

Получите лицензию прямо из браузера — без локальной установки .NET или Docker:

1. Для `workflow_dispatch` требуется доступ на запись к репозиторию, поэтому если вы не являетесь его соавтором, **сначала форкните этот репозиторий**, а затем откройте вкладку **Actions** в своём форке (если появится предложение включить workflows — это разовый шаг для нового форка).
2. Откройте **Actions > CI/CD > Run workflow**.
3. Заполните те поля, которые хотите изменить, — имя, компания, email, план, количество пользователей, год истечения срока действия, дополнения, — либо отметьте «regenerate keys», чтобы получить собственную уникальную пару ключей вместо общей пары по умолчанию, а остальные оставьте как есть.
4. Запустите workflow, а затем скачайте артефакт `gitlab-license` из завершённого запуска: он содержит лицензию, её JSON в открытом виде и соответствующий публичный ключ. **Скачайте его сразу** — он истекает через 1 день (минимальный срок хранения в GitHub), как и у ежедневного планового запуска ниже.

Этот же workflow также запускается автоматически каждый день в 09:00 UTC с настройками по умолчанию — этот плановый запуск лишь проверяет работоспособность пайплайна и не является каналом распространения лицензий, поэтому для лицензии, которую вы действительно собираетесь установить, используйте шаги 1–4 выше.

## Конфигурация

Все настройки находятся в секции `License` файла `appsettings.json` (`src/GitlabLicenseGenerator.Cli/appsettings.json`), который поставляется рядом с исполняемым файлом. Редактировать его для получения рабочей лицензии никогда не требуется — каждое значение по умолчанию уже предоставляет максимальные права.

| Параметр | Значение по умолчанию | Описание |
| --- | --- | --- |
| `Name` | `Tim Cook` | Имя лицензиата |
| `Company` | `Apple Computer, Inc.` | Компания лицензиата |
| `Email` | `tcook@apple.com` | Email лицензиата |
| `Plan` | `ultimate` | `ultimate`, `premium` или `starter` |
| `UserCount` | `2147483647` | Количество активных пользователей / мест |
| `ExpireYear` | `2500` | Год истечения срока действия лицензии (месяц и день — всегда 1 апреля) |
| `IncludeAddOns` | `true` | Также предоставлять все дополнения GitLab Duo и другие дополнения на основе мест |
| `PublicKeyPath` | `keys/public.key` | Путь, по которому считывается/записывается публичный RSA-ключ — репозиторий поставляет здесь пару ключей по умолчанию |
| `PrivateKeyPath` | `keys/private.key` | Путь, по которому считывается/записывается приватный RSA-ключ — репозиторий поставляет здесь пару ключей по умолчанию |
| `RegenerateKeys` | `false` | Установите `true` один раз, чтобы заменить общую пару по умолчанию новой, приватной парой, принадлежащей только вам |
| `OutputPath` | `output/result.gitlab-license` | Путь, по которому записывается зашифрованный файл лицензии (использованный публичный ключ копируется рядом с ним — приватный ключ GitLab никогда не нужен) |
| `PlainLicensePath` | `output/license.json` | Необязательная копия JSON лицензии в открытом виде — для проверки |

Чтобы переопределить настройку без редактирования файла, задайте переменную окружения, используя стандартное для .NET соглашение о двойном подчёркивании для вложенных ключей — именно так поступают все примеры выше (и Docker-образ):

```bash
export License__Name="Ada Lovelace"
export License__ExpireYear=2100
```

### Примечание по безопасности: общая пара ключей по умолчанию

Файлы `keys/private.key` и `keys/public.key` зафиксированы в этом репозитории, поэтому инструмент работает сразу после клонирования или форка — без какого-либо шага генерации. Это также означает, что **во всех клонах и форках используется абсолютно одна и та же пара ключей** — с её помощью кто угодно может расшифровать или переподписать файл `.gitlab-license`. На практике для реального сценария использования этого инструмента это компромисс с низким риском: установка собственного публичного ключа на экземпляр GitLab и без того требует прав root/администратора на этом экземпляре, поэтому общая пара ключей не даёт злоумышленнику ничего такого, для получения чего ему не нужны были бы более высокие привилегии. Тем не менее инструмент по-прежнему предназначен **только для локального использования и разработки** — если вам нужна пара ключей, которая есть только у вас, удалите `keys/private.key` и `keys/public.key` (или один раз установите `License__RegenerateKeys=true`) перед тем, как сгенерировать лицензию, которую вы будете устанавливать по-настоящему. Каждый запуск также копирует использованный публичный ключ в (игнорируемый Git каталог) `output/` рядом с лицензией — это локальная копия для удобства того же публичного ключа, что описан выше, а не новый или дополнительный ключ, поэтому это никак не меняет описанную картину. Приватный ключ никогда не копируется за пределы `keys/`.

## Установка лицензии

Как только у вас есть `keys/public.key` и `output/result.gitlab-license`:

### 1. Замените публичный ключ шифрования лицензии GitLab

GitLab считывает публичный ключ шифрования лицензии по фиксированному пути внутри экземпляра: `/opt/gitlab/embedded/service/gitlab-rails/.license_encryption_key.pub`. Вы должны перезаписать его публичным ключом, сгенерированным этим инструментом, иначе лицензия, которую вы установите на шаге 2, будет отклонена. (`output/public.key` из того же запуска генерации — это идентичная копия, и её можно использовать взаимозаменяемо с `keys/public.key` ниже.)

**Docker / docker-compose** — смонтируйте его в режиме только для чтения в вашем собственном `docker-compose.yml` (полный пример см. в `examples/docker-compose.gitlab-ee-19.3.yml`):

```yaml
services:
  gitlab:
    image: gitlab/gitlab-ee:19.3.0-ee.0
    volumes:
      - ./keys/public.key:/opt/gitlab/embedded/service/gitlab-rails/.license_encryption_key.pub:ro
      # ...your other GitLab volumes/config
```

Затем, когда контейнер запущен, выполните reconfigure:

```bash
docker exec gitlab gitlab-ctl reconfigure
docker exec gitlab gitlab-ctl restart
```

**Установка на выделенный сервер / Omnibus**:

```bash
sudo cp ./keys/public.key /opt/gitlab/embedded/service/gitlab-rails/.license_encryption_key.pub
sudo gitlab-ctl reconfigure
sudo gitlab-ctl restart
```

### 2. Загрузите лицензию в GitLab

1. Войдите в GitLab под учётной записью администратора.
2. Перейдите в **Admin Area > Settings > General**.
3. Найдите раздел **«Add License»**, загрузите файл `output/result.gitlab-license`, отметьте флажок Terms of Service и нажмите **Add License**.
4. GitLab перенаправит вас в **Admin Area > Subscription**, где вы в любой момент можете просмотреть установленную лицензию (а если она включает дополнения — предоставленные ею места GitLab Duo).

> В текущих версиях GitLab страницы `/admin/license/new` больше не существует — форма загрузки находится на странице General settings, указанной выше.

### Дополнительно: отключение Service Ping

```bash
sudo nano /etc/gitlab/gitlab.rb
```

```ruby
gitlab_rails['usage_ping_enabled'] = false
```

```bash
sudo gitlab-ctl reconfigure
sudo gitlab-ctl restart
```

## Тестирование на локальном экземпляре GitLab

`examples/docker-compose.gitlab-ee-19.3.yml` — это эталонный сервер GitLab EE, заранее настроенный для приёма лицензии от этого инструмента (он уже монтирует `../keys/public.key` по нужному пути). Он **не** является частью генератора — он предоставлен исключительно для того, чтобы у вас было на чём протестировать сгенерированную лицензию:

```bash
export GITLAB_HOME=/srv/gitlab
mkdir -p "$GITLAB_HOME/config" "$GITLAB_HOME/logs" "$GITLAB_HOME/data"
docker compose -f examples/docker-compose.gitlab-ee-19.3.yml up -d
```

## Как это работает

- **`GitlabLicenseGenerator.Core/Crypto`** — генерация RSA-ключей и конверт шифрования лицензии (GitLab шифрует свой JSON лицензии по схеме RSA/AES; публичная половина поставляется вместе с GitLab, приватная остаётся у того, кто выпускает лицензии).
- **`GitlabLicenseGenerator.Core/Licensing`** — строит, проверяет, сериализует и экспортирует лицензию:
  - `LicenseFeatureCatalog` — все символы функций EE Ultimate, которые собственная константа GitLab `FEATURES_BY_PLAN` сопоставляет с планом `ultimate`.
  - `LicenseAddOnCatalog` / `LicenseAddOnPurchase` — механизм дополнений на основе мест (`restrictions.add_on_products`), предоставляющий GitLab Duo Pro, Duo Enterprise, Duo with Amazon Q, Duo Core, Duo Agent Platform Self-Hosted, GitLab Credits, Secrets Manager и Flex Offline. Это работает только для **офлайн-облачной лицензии** (`cloud_licensing_enabled` + `offline_cloud_licensing_enabled`, которые этот инструмент всегда устанавливает).
  - `LicenseFactory` — объединяет всё вышеперечисленное в единый `License` с максимальными правами.
  - `LicenseValidator` / `LicenseCodec` / `LicenseJsonConverter` — валидация, JSON-схема, совместимая с GitLab, а также шифрование/экспорт.

## Устранение неполадок

- **HTTP 502 от GitLab**: подождите, пока он завершит запуск — при первом старте это может занять несколько минут.
- **Лицензия отклонена**: убедитесь, что вы заменили `.license_encryption_key.pub` *соответствующим* файлом `keys/public.key` из того же запуска генерации, что и загружаемая лицензия, и что вы перезапустили GitLab после копирования ключа.
